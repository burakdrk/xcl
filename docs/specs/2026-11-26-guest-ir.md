# Guest IR for console shaders — design and roadmap (2026-11-26)

Fork `burakdrk/xcl`, branch `guest-ir/design`, based on `main` at `8b957bec`. This is a
learning project and is not proposed upstream. If it shows measured gains, the way upstream is
a proposal on xcl-dev/xcl#2088 with the numbers, then PRs split as `CONTRIBUTING.md` asks.

## Goal

Translate console RDNA2 programs through an intermediate representation of XCL's own: a
*guest IR* that still describes the console program (its 64-lane wave, its registers, EXEC,
its descriptors). Lower that IR to DXIL with the existing `gpu/dxil` layers:

```
RDNA2 decode → guest IR (SSA) → guest-level passes → lowering to DXIL → DXIL cleanup → container + signature
```

What it is for, in order:

1. **A smaller, simpler program for the driver.** Cold driver compile time is the measured
   bottleneck (see "What compile time is made of"). Passes that know the program came from a
   console can remove work the driver cannot prove removable: EXEC guards that always hold,
   redundant cross-lane reads, mask round trips, repeated code.
2. **One place for the direct path's instruction semantics.** Today the semantics in
   `recomp/emit.rs` are written again by each direct translator.
3. **A place where console-level analyses change the program**, not only annotate it:
   lane masks, wave64 exchanges, descriptor origins, BVH traversal loops.
4. **Something to read:** the IR has a text form, printable after the frontend and after each
   pass.

### Non-goals

- Replacing the HLSL path. It stays the fallback for everything the new path refuses.
- Changing the shader ABI (root signature, `io` / `res` / `mem`, memory windows, heaps, static
  samplers), the pipeline code outside shader translation, or the cache format beyond a new
  identity.
- Vulkan / SPIR-V.
- Upstreaming as is.

## Background: XCL today

### Three translators

| Path | Code | Stages | Chosen by |
|---|---|---|---|
| HLSL → DXC | `gpu/recomp/emit.rs` (6 851 lines: "one RDNA2 instruction → HLSL statements"), `recomp/mod.rs`, `recomp/dxc.rs` | all | default |
| Direct, per-instruction form (#1426) | `gpu/dxil/lower*.rs` (9 files, 11 262 lines), `lanes.rs`, `cfg.rs`, `ssa.rs`, `kernel.rs`, `graphics.rs`, `compact.rs` | CS, mesh compute pass; VS / PS; ES+GS | `XCL_DIRECT_DXIL=1` (compute), `=all` (VS / PS); also compute programs whose HLSL exceeds 8 MB (#2120) |
| Direct, per-lane form (#1745) | `gpu/recomp/lower.rs` (4 565), `lower/wave.rs`, `lower_dxil.rs` (1 169), `recomp/ssa.rs` | CS | `XCL_PER_LANE=1` with `XCL_DIRECT_DXIL` |

The compute order is in `recomp/pso.rs` (`compile_console_shader`, `direct_compute`): the
per-lane form (when on), then the per-instruction form, then HLSL. Each fallback is recorded by
`gpu/dxil/coverage.rs` (`record_fallback`). The per-lane form hands what it cannot lower to the
per-instruction form's semantics through `Ir::foreign` → `Lw::inst_guarded`
(`recomp/lower_dxil.rs`, `gpu/dxil/lower.rs`).

All three take `emit.rs` as the semantic reference (`gpu/dxil/lower.rs`: "the semantic
reference for every instruction"), and each of them writes those semantics again.

Pieces they share, which this design reuses:

- decoding: `gpu/rdna2.rs` (tables generated by `scripts/gen_rdna2.py`), `rdna2::resolve_far_jumps`;
- analyses on decoded code:
  - `recomp/lane_masks.rs`: lane masks as per-lane booleans, used by the per-lane form;
  - `recomp/x64_masks.rs`: masks whole-live in the split form;
  - `recomp/upper_lanes.rs`: what lanes 32..63 hold;
  - `recomp/partition.rs`: whether a split is exact;
  - `recomp/cfg.rs`: post-dominators, control dependence;
- the DXIL layers: `gpu/dxil/{bitstream,module,shader,ops,container}.rs`;
- cleanup and shaping:
  - `gpu/dxil/module/opt.rs`: `Module::optimize`, run when a shader is finalised;
  - `gpu/dxil/compact.rs`: the compact form;
  - `gpu/dxil/module/split.rs`: splitting at CFG edges.

### The direct path has an IR already, at the target's level

The per-instruction form builds SSA over register dwords straight into an in-memory DXIL
module, and `opt.rs` cleans that module. In its own words, the translator "emits each guest
instruction's per-lane expansion as is (repeated lane-bit / ballot / extract sequences,
operands of discarded results); this pass removes the redundancy". At that level an
instruction is a dozen `dx.op` calls. What it meant on the console (a `v_readlane` of a uniform
value, a V# loaded from user data) is no longer visible to a pass.

The per-lane form's `Ir` trait (`recomp/lower.rs`) is the closest thing to a backend-neutral
interface. It has integer ops, compares, `select`, `ballot` / `ballot_half`, `read_lane` /
`read_lane_half`, `whole_needs_exchange`, raw `io` / `res` / `mem` access and `foreign`. It
"maps one to one onto the builder", so it is a lowering interface, not a guest IR. This design
keeps its split between cross-lane operations that need the whole wave and those that stay
within a 32-lane half.

### Wave size

A console program is wave32 or wave64 (the FSSM flag, #573). D3D12 allows `[WaveSize]` only on
compute shaders. On an adapter with `WaveLaneCountMax < 64` (NVIDIA), a `[WaveSize(64)]`
compute shader is rejected at PSO creation (`docs/wave64-on-wave32.md`). XCL's forms today:

- **native:** one hardware wave per console wave (wave32 programs, and wave64 where the
  adapter runs 64-lane waves);
- **split:** a console wave64 is two hardware wave32s of one thread group. They exchange
  ballots, `v_readlane` values and GLC scalar loads through groupshared memory. Used for
  compute and kernel mode, the mesh first pass, and ES+GS;
- **upper lanes:** a wave64 VS / PS on 32-lane hardware cannot be paired, so `upper_lanes.rs`
  supplies what lanes 32..63 hold where the program reads them.

Mesh programs run in two passes: a compute pass that runs the program, then a pass-through
mesh shader that draws its output (`recomp/mod.rs`). The console code relies on 64-lane
ballots, and only compute can ask for a wave size.

### What compile time is made of (measured upstream)

- **#1096** (RTX 3050, `main` at 67a3735, 424 variants of a retail pack):
  - Translation took 6 s and DXC 1 819 s, so translation is 0.3 % of DXC.
  - DXC takes about 2 ms per console instruction.
  - The driver takes 97–106 s for an 18k-instruction compute shader, about 5× DXC.
  - DXC `-O3` against `-O0` halves the DXIL and leaves the driver's time unchanged.
- **#2088:** a cold pass over 879 pipelines kept all 12 driver slots busy. The largest
  program, about 4 MB of DXIL, took 951 s in the NVIDIA driver.
- **What has moved driver time is structure, not generic optimisation:**
  - the compact form (#2034, #2120): programs of 15–30 MB of HLSL became about 0.5 MB;
  - splitting at CFG edges (#2080): 5.8–10.3× lower cold build wall time, at 1.57–2.06× GPU
    time on its tested shader (as quoted in #2088);
  - #1630 (open; its author's numbers): an RDNA2-level CFG / liveness optimiser in front of
    the HLSL emitter, −31.2 % cold driver time on 12 retail compute shaders (GTX 1070).

So the IR's passes are judged by what they do to the driver's input (DXIL size, blocks,
instructions) and to GPU time, which must not get worse unnoticed.

## Prior art: KytyPS5

KytyPS5 (github.com/KytyPS5/KytyPS5) is a PS5 translation layer. The PS5 GPU is RDNA2 too.
It is written in C++ and targets Vulkan 1.3, emitting SPIR-V. Read at commit `61db2f88`
(2026-11-26): `ShaderRecompiler.cpp`, `frontend/cfg/ShaderCFG.{h,cpp}`,
`frontend/translate/Control.cpp`, and in `backend/spirv/` the files `spirvEmitterProgram.cpp`,
`spirvEmitterModule.cpp`, `spirvEmitterMesh.cpp`, `spirvEmitterRayQuery.cpp` and
`spirvEmitterBvh.cpp`, plus `ir/passes/RayQueryTraversal.cpp` and `Tessellation.cpp`.

Pipeline (`ShaderRecompiler.cpp`):

1. Decode (`frontend/decode`), build the CFG and structure it, with a dispatcher fallback
   when structuring fails (`frontend/cfg/ShaderCFG.cpp`).
2. Translate to its own IR (`ir/opcodes/ValueOpcodes.inc`, `frontend/translate`).
3. Passes:
   - `RewriteToSsa`;
   - `ConstantPropagationPass` + `RemoveIdentities` + `EliminateDeadCode`;
   - `EliminateReadLane`, then the cleanup again;
   - `TrackResources`. `ResourceTracking.cpp` (216 KB) is the largest file of the recompiler;
     `SrtWalker.cpp` walks the PS5 Shader Resource Table.
4. Per bound resource state:
   - `ApplyResourceSpecialization`, then cleanup;
   - optionally `TraceTraversalsWithRayQueries`, which replaces the game's BVH traversal loop
     by a Vulkan ray query against a mirror structure the host builds;
   - `CollectShaderInfo`;
   - SPIR-V emission through its own builder.

**Wave64 on 32-lane GPUs:** with `lane_count == 2`, the emitter writes every IR instruction
twice in the same invocation, once per 32-lane half. Whole-wave results (ballot,
`ReadFirstLane`, reductions, scalar loads) are computed once and shared
(`spirvEmitterProgram.cpp`). I did not find where `lane_count` is chosen.

**Mesh shaders:** the guest program runs inside the Vulkan mesh shader, followed by a barrier
and `OpSetMeshOutputsEXT`, all in one pass (`spirvEmitterMesh.cpp`).

What carries over:

- the layering: guest IR → passes → emitter;
- the pass list;
- resource tracking with specialisation, as an idea;
- ray-query recognition;
- two lanes per thread, as an experiment.

What does not:

- the SRT resource model: Xbox titles bind through D3D12-style root signatures and console
  descriptor heaps;
- what follows from Vulkan's buffer device address, such as needing no memory windows;
- the SPIR-V emitter.

yuzu and shadPS4 use the same layering (guest ISA → own SSA IR → passes → SPIR-V), as far as
is publicly known. This was not checked for this document.

## Design

### Module layout

New code goes under `crates/xcl/src/gpu/gir/` ("guest IR"; the name keeps clear of
`recomp::lower::Ir`):

| File | Content |
|---|---|
| `mod.rs` | `Program`, `Block`, `Inst`, `Op`, `Ty`, `ValueId`; `enabled()` |
| `build.rs` | builder: blocks, instructions, phis |
| `print.rs` | text form |
| `verify.rs` | SSA, type and uniformity checks |
| `front/` | RDNA2 → gir, one file per instruction family (`salu`, `valu`, `vopc`, `smem`, `buffer`, `image`, `flat`, `lds`, `export`, `flow`) |
| `pass/` | pass manager; `cleanup`, `lanes`, `readlane`, `wave64`, `resources`, `rayquery` |
| `interp.rs` | CPU interpreter (tests only) |
| `lower/` | gir → DXIL: `mod.rs`, `wave.rs` (wave forms), `entry.rs` |

Existing files are touched only at hooks:

- `recomp/pso.rs`: routing and the cache identity;
- `recomp/runner.rs`: the backend switch for kernel tests;
- `shaders.rs`: the CLI flags;
- module declarations.

That keeps rebasing onto upstream, where `gpu/dxil` changes often, cheap.

### Data model

**Program:** the stage, the console wave size, the interface (`CsInterface`, or the VS / PS
signatures from `ISG1` / `OSG1` / `PSV0` as today), the blocks, a value arena, and the float
mode (FSSM and the initial MODE).

**Values:** a `ValueId` into the arena. Every value has a type and a uniformity.

- Types: `U1`, `U16`, `U32`, `U64`, `F16`, `F32`, `F64`. There are no vectors: a register
  dword is the unit. An op with several results (add with carry, multi-dword loads) returns a
  tuple, read with `Proj`.
- Uniformity: **Uniform** (the same in every lane of the console wave: what SGPRs, SCC, and
  VCC / EXEC as numbers hold) or **Varying** (per lane: VGPRs, a lane's bit of a mask).
- The rule, from the execution model in `docs/wave64-on-wave32.md`: a Uniform value depends
  only on Uniform values, scalar memory, or a whole-wave op (`Ballot`, `ReadLane`,
  `ReadFirstLane`, a reduction). The verifier checks this. The split form depends on it,
  because both halves must compute identical Uniform values.

**Masks:** a lane mask is a Uniform `U64` (`U32` in wave32), the console's number. Its
per-lane view is `LaneBit(mask) → U1 Varying`. The reverse is `Ballot(b, exec) → U64 Uniform`:
the bits of the lanes in `exec` where `b` holds.

**The EXEC model** is exact, as in all three translators today: every lane runs every
instruction, and EXEC only masks effects.

- A VGPR write is `Select(LaneBit(exec), new, old)`.
- Stores, atomics, LDS writes, exports and lane writes carry a `guard: U1 Varying` operand.
- Compares and carries produce `Ballot(result, exec)`.

The `lanes` pass removes the selects and guards it proves redundant, and turns mask branches
into per-lane branches. No other pass needs to know about EXEC.

**Control flow:** a block starts with its phis and ends with a terminator:

- `Jump`;
- `Branch(cond: U1 Uniform)`, the console's scalar branches;
- `LaneBranch(cond: U1 Varying)`, created only by the `lanes` pass;
- `End` (`s_endpgm`).

An indirect jump that `resolve_far_jumps` leaves unresolved is refused, as today.

**Cross-lane ops** are defined over the console wave and fall into two classes, as in
`recomp/lower/wave.rs`. The class tells the lowering whether the split form needs an exchange.

- *Whole wave:* `Ballot`, `ReadLane(v, lane: Uniform)`, `ReadFirstLane`, `WriteLane`,
  `Bpermute(v, lane: Varying)`, `MbcntLo`, and masks used as numbers (`CountBits`,
  `FindFirst`).
- *Within a 32-lane half:* DPP16 / DPP8, `Permlane16` / `PermlaneX16`, `Swizzle`, `MbcntHi`.

**Arithmetic:** integer, float, conversion, compare and select ops at the level of what the
ISA defines, not of DXIL. Exactness is part of the op:

- `FMul { legacy }`, for `v_mul_legacy_f32`'s 0·x = 0;
- min / max with RDNA's NaN rules;
- the rounding and denorm mode on every float op, from FSSM / MODE and `s_setreg`,
  `s_round_mode`, `s_denorm_mode`;
- no fast-math.

16-bit `op_sel`, SDWA and DPP selects are explicit extracts and inserts. Source modifiers
(abs, neg) and output modifiers (clamp, omod) are separate ops, so passes can fold them.

**Memory and resources:** descriptors are operands holding the raw dwords, Uniform values as
in hardware: V# is 4 dwords, T# 8, S# 4. The ops:

- `ScalarLoad(base: U64, offset, n, glc)`;
- `BufferLoad` / `Store` / `Atomic(V#, voffset, soffset, offset, format, n, cache bits)`;
- `GlobalLoad` / `Store` / `Atomic(addr: U64 Varying)` and the flat forms;
- `LdsLoad` / `Store` / `Atomic`;
- `ImageSample` / `Gather4` / `Load` / `Store` / `Atomic` / `Resinfo` / `GetLod(T#, S#, coords, dmask, d16, …)`;
- `BvhIntersect(node, ray, T#)`.

The `resources` pass may later replace a descriptor operand by a `Binding` it has traced.

**Stage I/O:**

- `Input(kind)`: user SGPR k, thread and group ids, vertex and instance id, ISG1 element r.c,
  the PS input VGPRs by `SPI_PS_INPUT_ENA`;
- `Interp(attr, i, j, mode)`;
- `Export(pos / param / mrt / mrtz / prim, values, done, guard)`;
- `MeshAlloc(vertices, primitives)` (`s_sendmsg` GS_ALLOC_REQ);
- GS emit / cut;
- `Barrier`, `ReadClock`.

**Foreign:** `Foreign { inst, guard, inputs, outputs }` stands for an instruction the frontend
does not model yet. It is lowered by #1426's `Lw::inst_guarded`, the way `DxilIr::foreign`
already does it for the per-lane form (`recomp/lower_dxil.rs`). Passes treat it as opaque: it
reads its inputs, writes its outputs and has side effects. This lets the pipeline run end to
end from the first phase. Each instruction family moves out of `Foreign` with its tests.

**Text form** (`print.rs`), for `--gir-dump` and the pass tests:

```
b0:
  %1:u32.u   = input user_sgpr 0
  %2:u32.v   = input thread_id.x
  %3:u1.v    = icmp ult %2, %1
  %4:u64.u   = ballot %3, exec %0
  %5:u32.u   = countbits %4
  branch %6, b1, b2
```

### Frontend

- **Input:** the decoded program (`rdna2::decode`, `resolve_far_jumps`), its blocks
  (`gpu/dxil/cfg.rs`), and the stage interface as `pso::direct_compute` builds it today.
- **Registers become SSA values** through the on-the-fly construction already in
  `recomp/ssa.rs`: `Ssa<V>` with a `Sink` for gir, variables `S(n)`, `V(n)` and `Scc`. No third
  implementation of Braun et al. is written.
- **Semantics:** one function per instruction family, with `emit.rs` as the reference. Each
  family is checked by the GPU instruction tests and by the interpreter.
- **Code-relative constants** (`s_getpc_b64`), the VS fetch-shader call (`s_swappc_b64`) and
  trampolines are handled as the current direct translators handle them. Whatever they refuse,
  gir refuses.

### Passes

The pass manager:

- runs an ordered list, with the verifier after each pass in tests and with `XCL_GIR_VERIFY=1`;
- lets `XCL_GIR_PASSES=-name,…` switch passes off for bisecting, as `XCL_DXIL_NO_OPT` does
  for `opt.rs`;
- logs per-pass statistics: instructions, blocks, phis, selects, guards, exchanges.

| Pass | Does | From | Phase |
|---|---|---|---|
| `cleanup` | constant folding, identities, trivial phis, CSE (pure ops along the dominator tree, cross-lane ops only within a block), DCE; also runs after every other pass | Kyty's cleanup trio; `opt.rs`'s rules | 5 |
| `lanes` | drops EXEC selects and guards that always hold; mask branches become `LaneBranch` where exact; `LaneBit(Ballot(x))` → x in the lanes that are active | `recomp/lane_masks.rs` (BDD of atoms, reaching facts) on gir | 5 |
| `readlane` | `ReadLane` / `ReadFirstLane` of a Uniform value → the value; reductions recognised | Kyty's `ReadLaneElimination` | 5 |
| `wave64` | analysis only: which masks and values need a whole-wave exchange in the split form, whether the halves partition exactly, what upper lanes hold in VS / PS; feeds the choice of wave form | `x64_masks.rs`, `partition.rs`, `upper_lanes.rs` | 3 (exchanges), 7 (VS / PS) |
| `resources` | trace descriptor operands to their sources; specialise | Kyty's approach; needs its own design round (open questions) | 6 |
| `rayquery` | the game's BVH traversal loop → `RayQuery`, else keep `BvhIntersect` | Kyty's `RayQueryTraversal` | 8 |

**Shape** (the compact form, splitting) stays in `gpu/dxil` at first (`compact.rs`,
`module/split.rs`). It is applied to the gir lowering's output as it is to the current direct
path's. It moves to the IR only if it measures better there.

### Lowering

- **Target:** the `gpu/dxil` builder (`module.rs`, `shader.rs`, `ops.rs`). Entry setup and
  finish come from `dxil/kernel.rs` (kernel ABI and CS ABI) and `dxil/graphics.rs` (VS, PS,
  MS). The ABI is unchanged, so `pso.rs` creates pipelines as it does for the direct path.
- **Wave forms:** a trait used by whole-wave and half-wave ops (ballot, read lane, their half
  forms, the barriers they need), with these implementations:
  - `Native`;
  - `Split`, as in `docs/wave64-on-wave32.md`, exchanging only where `wave64` says;
  - `UpperLanes`, for VS / PS;
  - `Doubled`, an experiment for compute and mesh only: two console lanes per thread, Kyty's
    form.

  The form is chosen per program from the stage, the console wave size, the adapter
  (`WaveLaneCountMax`) and `KernelOptions::split`, as today.
- **Foreign** ops are lowered by `Lw::inst_guarded`.
- **Memory windows** are lowered as now (`gpu/dxil/lower_window.rs`, `XCL_HEAP_WINDOWS`).
- **After lowering**, `Module::optimize` runs as today. Whether it still pays is measured with
  `XCL_DXIL_NO_OPT=all`.

### Integration

- **Switch:** with `XCL_GIR=1`, compute programs (kernel tests and `pso::direct_compute`) try
  gir first and then the existing chain. Graphics follows later, as `XCL_GIR=all`.
- **`pso::direct_compute`:** gir → per-lane (when `XCL_PER_LANE=1`) → per-instruction → HLSL.
  The fallback is recorded as `"CS gir"` through `record_fallback`.
- **Cache:** the translated cache gets an identity of its own (a `Backend` tag and a
  `GIR_VERSION`), never mixed with other entries (the `translated` module in `pso.rs`).
- **Tests:** `runner.rs` translates kernels through gir with `XCL_GIR=1`, as
  `XCL_DIRECT_DXIL=1` does today.
- **Tools:**
  - `xcl shaders <pack> --gir [--sample N] [--seed S] [--validate] [--compare]`: per program,
    translated, the number of Foreign ops, or refused with a reason; a ranked histogram of what
    it refuses and DXIL size against the other backends, as `--direct` gives;
  - `--gir-dump HEX`: the IR after the frontend and after each pass;
  - `--measure-pso HEX --backend gir|direct|hlsl`: today `--measure-pso` times the HLSL path
    only.

### Testing

1. **Unit tests** in each module: builder, printer, verifier, and each pass on hand-written
   programs, compared as text before and after.
2. **CPU interpreter** (`interp.rs`): runs a gir program over a 64-lane wave. It covers ALU,
   control flow, masks, cross-lane ops, and flat and LDS memory as byte arrays; no images,
   no BVH. It is used for:
   - **pass checks:** each pass, on random register files, must give the same final state
     before and after. This runs on the instruction tests' programs, and locally on a corpus
     sample;
   - **frontend checks:** interpreter results against the expected results of the recompiler's
     instruction tests, without a GPU.

   Floats are compared bit for bit where the IR defines the result exactly. Approximations
   (`v_rcp`, `v_sqrt`, `v_sin`, …) are compared with the same tolerance the GPU tests use.
3. **GPU:** the recompiler's instruction tests (`gpu/recomp/tests.rs` through `runner`) with
   `XCL_GIR=1`, against the same expected results as the HLSL path and `XCL_DIRECT_DXIL=1`.
   Report the counts and the `SKIPPED` tests as `AGENTS.md` asks.
4. **Corpus:** `--gir --validate` on a seeded sample of a pack: translation rate, validator
   results, and Foreign ops per opcode. Game data stays outside the repository; results are
   kept as counts and hashes.
5. **The whole suite** (`cargo test --workspace -- --test-threads=4`) before anything is merged
   into the fork's `main`.

### Measurement protocol

For every phase that changes generated code:

- **Sample:** a fixed list of record hashes, kept outside the repository. For example, a
  seeded 1-in-40 sample of a pack (as #1096 used) plus a dozen of its largest compute programs.
- **Per program and backend** (hlsl, direct, gir):
  - translation time;
  - DXIL size;
  - blocks and instructions in the DXIL;
  - cold driver PSO time (`--measure-pso`, driver cache off, `--repeat 3`);
  - GPU time per dispatch. The tool for this is still open: a timed replay through `runner`,
    or PIX.
- **Hardware:** an NVIDIA GPU (32-lane waves, where the driver wall is), and AMD when available.
  Name the GPU, the driver and the commit.
- **Keep a pass** if it lowers driver time or DXIL size without raising GPU time beyond noise.
  Report both numbers either way.

The whole game is needed only for smoke runs. Everything else works on the test suite or on
single programs from `shaders.rpf`. Commands assume `. .\local\env.ps1`. Times are from this
machine (debug tests after an incremental build; `xcl` in release).

|---|---|---|
| every edit | `cargo test -p xcl --lib gpu::gir` | new; seconds expected |

| PRs that change generated code: coverage | `& $XclRelease shaders $XclPack --gir --sample 200 --seed 1 --validate --compare` (`--direct` today; `--max-bytes 0` includes programs over 16 KB) | direct: 167 programs in 0.6 s; with `--compare`, 33 programs in 1.7 s |
| PRs that change generated code: driver time | `& $XclRelease shaders $XclPack --measure-pso HEX --repeat 3` for each hash of the fixed list | 0.72 s median for 94 KB of DXIL (DXC 575 ms) |
| phase 0 | `& $XclRelease shaders $XclPack --top 50` | 3 s |
| before merging into the fork's `main` | `cargo test --workspace --no-fail-fast -- --test-threads=4`, compared with the baseline | about 1 min |
| PRs that change the runtime path | `.\scripts\smoke.ps1 -Game $XclGame -Seconds 60`, from `main` and from the head, with and without `XCL_GIR=1` | needs Gaming Services |

Notes on the tools:

- **`--measure-pso` times the HLSL path only today**, so phase 4 adds `--backend`.
- **Finding compute programs:** `--export-hlsl <temp dir> --min-kb K --count N` prints
  `<hash>.hlsl` for each compute program. The sweep's dumped DXIL cannot tell them apart,
  because the compute pass of a mesh program is a compute shader too.
- **The sweep prints the game's shader names.** Keep its output in `local/`, and write only
  hashes and counts anywhere else.

## Open questions and risks

1. **Do guest-level passes reduce driver time?** This is the bet the whole design rests on.
   - For: #1630's RDNA2-level optimiser (−31.2 % driver time, its author's numbers, open PR).
   - Against generic passes: #1096 (DXC `-O3` did not move driver time).

   Phase 5's first pass is the test. If it moves nothing, the design's value is limited to
   points 2–4 of the goal.
2. **Specialisation against variant count.** Each specialised variant is another driver
   compile, which is the bottleneck. Specialise only on what is fixed when the pipeline is
   created, not on what changes per draw.
3. **Proving memory windows at translation time** needs runtime addresses, so it would mean
   per-dispatch variants. That is probably not worth it. Heap-indexed windows
   (`XCL_HEAP_WINDOWS`) already cut the selection code.
4. **How descriptors reach shaders today** (console descriptor heaps, `gpu/desc.rs`, heap
   windows, user data) has to be mapped before `resources` is designed. `recomp/pso.rs` still
   calls the mapping of the title's root arguments "the next step", which may be out of date.
5. **Upstream churn.** `gpu/dxil` changes daily, and `Foreign` ties gir to `Lw`'s internals.
   Rebase often and keep the hooks small.
6. **A fourth translator.** That is acceptable in a learning fork. If it wins, the end state is
   gir replacing both direct forms (`gpu/dxil/lower*.rs`, `recomp/lower.rs`), whose semantics
   would then live in `gir/front`.
7. **Translation time.** It is 0.3 % of DXC today; the IR and its passes must stay small next
   to the driver. Measure it.
8. **`Doubled` doubles the code** handed to the driver, which may cost more compile time than
   it saves. Measure before relying on it. It cannot apply to VS / PS: one pixel per
   invocation.
